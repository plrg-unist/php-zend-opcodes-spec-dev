# Differential testing against the Zend Engine

The [printer and loader tests](extension-testing.md) exercise the full codec corpus. The [semantics suite](../scripts/test_semantics.py) compares executions within the [agreed runtime scope](semantics-scope.md).

## Spec executable and differential suite

- `zend-opcodes [--json] [--constants FILE] [--constant NAME=JSON ...] [installation flags] FILE.zop` reads the program from the path and PHP input from process stdin. In normal mode forward program stdout and stderr and return its exit status, including for PHP failures. Non-PHP execution outcomes panic in this mode. Invalid command lines print a diagnostic to stderr and exit 2. A help request (`-h` or `--help`) prints plain text and exits 0.
- In JSON mode emit one object on stdout and exit 0 for all reported outcomes. A standalone `--json` selects this mode even after an invalid argument. Preserve literal `--json` in a filename after `--` or as an installation option's value. For `kind: "php"` include `stdout` and `stderr` as ordered arrays of integers from 0 to 255 and `exit_status` as the PHP process status. Python can recover each stream with `bytes(values)`. Use distinct kinds for `unsupported`, `malformed`, and `tool_error`. Preserve bytes already emitted before an unsupported operation. An evaluator defect or failed invocation fails the test. [CLI regression tests](../tests/installation.rs)
- Run `./scripts/test_semantics.py [-j JOBS] [PATH ...]`. It builds the executable once with `cargo build --bin zend-opcodes --message-format=json` and uses the path Cargo reports. Each job owns a temporary directory and one fixture/profile pair. Export PHP or PHPT with `php -l` once for that pair and reuse the listing for every input variant. Hand-written fixtures already supply the listing. The default is `os.cpu_count() or 1`. A positive `-j` value overrides it. [PHP fixture helper](../scripts/zend_fixtures.py) · [Compiler profiles](fixture-compilation.md) · [Cargo build messages](https://doc.rust-lang.org/cargo/reference/external-tools.html#json-messages)
- During development, select fixtures by absolute path or relative to the calling directory, for example `./scripts/test_semantics.py -j 4 tests/project/standalone_branches.zop`. Validate every supplied path against the semantics manifest before building or running any case. Deduplicate resolved paths. Each selected fixture runs both profiles and all its cases. For PHP outcomes compare stdout bytes, stderr bytes and exit status on the same listing, stdin and effective runtime constants in fresh Zend and spec processes. Exercise both normal and JSON spec execution.
- The [manifest](../tests/semantics.json) lists required executions. Each row names a `fixture` and optionally a raw `stdin` file, both relative to `tests/`. Omitted stdin means empty bytes followed by EOF. Store input bytes under `tests/stdin/<fixture-name>/`. Multiple rows can select different inputs for the same fixture. The default expectation is `php`. A PHP row may specify exact `stdout`, `stderr` or `exit_status` to check against each executor independently. For `expect` set to `unsupported`, optional `stdout` and `stderr` specify the bytes emitted before stopping. Both default to empty. A `malformed` row must fail before execution and produce no program output or coverage report. Only `php` rows run the native loader for this comparison. The codec suites keep discovering all program fixtures.
- A row's optional `constants` object overrides individual PHP values for that run. For example, `"constants": {"GLOB_MARK": 2}` overrides an integer. `constants_file` selects a complete base table relative to `tests/`. The default base is the repository's reference file. The differential runner supplies matching values to the spec and to Zend when loading the finalized listing. Native stream inputs refer to handles live in the reference request. [Value format](../design-docs/execution-io.md#runtime-constants) · [Per-run cases](../tests/semantics.json) · [Folded and runtime reads](../tests/project/runtime_constant_inputs.php)
- For a later-milestone feature, use a focused temporary `unsupported` expectation that reaches that operation through supported setup. An unexpected PHP result also fails this expectation. When the feature lands, normally keep the input, switch its expectation to `php`, and check its observable result against Zend. Revise or retire a redundant transitional case. Keep boundary cases for features permanently outside scope.
- An approved exception on a `php` row has a `divergence` object with a `rationale` path to an existing Markdown file under `design-docs/`, relative to the project root. Include only the differing `stdout`, `stderr` or `exit_status` fields. Each holds a pair such as `"stdout": {"zend": [49, 55], "spec": [55, 55]}`. Streams use octets and process statuses use integers from 0 to 255. In both profiles the test checks the pinned Zend value, the spec value in both execution modes, and direct agreement on every omitted field. Search the manifest for `"divergence"` to enumerate exceptions. [Approval policy](semantics-scope.md#choosing-what-to-model)

At file scope, `return 7;` and `return "7";` both finish with empty output and exit status 0. Check file-level return through its control-flow effect, such as skipping a later write. For a function result, make the calling fixture expose what matters. `exit(answer());` works for a small integer, and `exit(answer() === 7 ? 0 : 1);` checks both value and type. The initial suite compares only the three CLI observables. [CLI return handling](../../php-src/main/main.c#L2666)

## Spec coverage

Before reporting a milestone complete, run `./scripts/test_semantics.py` without fixture paths. This executes the full manifest and requires 100% cumulative structured-language (SL) instruction coverage, including when a job count is supplied. A run with explicit paths reports the selected coverage and permits gaps. A selection containing only malformed cases reports zero instructions executed. Every selected case must still meet its expectation.

For each instrumented run the script sets `ZEND_SPEC_COVERAGE` to a temporary report path. The executable attaches P4-SpecTec's `InstrHandler`, disables interpreter tail-call optimization so result instructions remain visible, and writes P4-SpecTec's per-step report separately from program output. Both execution modes use the runner's per-run pure-call cache so a shared literal subtree can be evaluated once. The script checks the report totals and the ordered step identities before combining passing cases. [Coverage implementation](../../p4-spectec/p4spectec/core/src/coverage/instr.rs) · [Execution host](../src/main.rs)

Combine hit IDs across fixtures, input variants and both compiler profiles. The full-suite gate requires a nonzero total and prints the owning definition and step for every miss. Use exact counts, include helper definitions and apply no coverage-ignore hints. If an invariant or lowering makes a counted step unreachable, investigate its purpose, simplify redundant rules when correct, and report any unresolved gap before declaring the milestone complete. [Report format](../../p4-spectec/p4spectec/core/src/coverage/log.rs)

At milestone review, check the [promised behaviors](semantics-roadmap.md) independently of the hit count. Identify what output or status would change for an incorrect result, which relevant operand and control-flow combinations the fixtures exercise, and which Zend behavior might lack a spec rule altogether.

The SL coverage report counts the spec instructions that call Rust primitives. Check each primitive's implementation separately with `cargo test` and with end-to-end cases against Zend. For binary64, exercise both sides of a rounding boundary and verify the printed bytes under ordinary output and diagnostics. [Rust numeric primitives and tests](../src/binary64.rs)

## Future VM observations

With the ordinary `php` executable alone, a fixture can explicitly print values or call `get_defined_vars()` in the scope of interest. Automatic VM checkpoints in an unmodified fixture need instrumentation. The existing extension could host an observer. For interactive inspection, the separate `phpdbg` executable supports `set stepping opcode` and `info vars`. [Scope variables](../../php-src/Zend/zend_builtin_functions.c#L1506) · [Debugger stepping](../../php-src/sapi/phpdbg/phpdbg_set.c#L216) · [Debugger variables](../../php-src/sapi/phpdbg/phpdbg_info.c#L36)

- **Returns and exceptions.** Zend’s call observer can receive a file or function return value while the frame is live. The error observer supplies diagnostic type, file, line and message. This permits differential checks of typed returns and exceptional completion when those observations are needed. [Return observation](../../php-src/Zend/zend_vm_def.h#L4546) · [Call observer](../../php-src/Zend/zend_observer.h#L49) · [Error observer](../../php-src/Zend/zend_observer.h#L152)
- **State checkpoints.** A user-opcode handler runs before the selected instruction. Record its body and index, read selected live locals or operands from `zend_execute_data`, and return `ZEND_USER_OPCODE_DISPATCH` to continue ordinary execution. Observe effects at the next appropriate checkpoint or frame exit, while the relevant values are live. Selected globals are available in `EG(symbol_table)`. For reachable state, compare PHP types, ordered array entries, stored object properties and object/reference identity using logical IDs. Allocator layout and addresses are process-specific. [Frame layout](../../php-src/Zend/zend_compile.h#L646) · [Opcode hooks and operand access](../../php-src/Zend/zend_execute.c#L5965) · [Global symbol table](../../php-src/sapi/phpdbg/phpdbg_info.c#L185) · [References](../../php-src/Zend/zend_types.h#L633)
- **Trace alignment.** Compare checkpoints within the same captured profile. OPcache can eliminate locals and instructions, and enabling a call observer can change frame sizing. Export the program during the observed run. Some handlers consume companion rows such as `OP_DATA`, so one dispatch can cover multiple instruction rows. [Observer frame slot](../../php-src/Zend/zend_opcode.c#L1146) · [Array assignment](../../php-src/Zend/zend_vm_def.h#L2680)

## Verified on the pinned engine

A temporary regular extension observed the same main and `bump` bodies that its compiler hook captured for this fixture.

```php
<?php
function bump(&$x) {
    $alias =& $x;
    $alias += 2;
    return $alias;
}
$n = 40;
$r = bump($n);
return [$n, $r];
```

With OPcache off and with its default optimizer, both output streams were empty and the exit status was `0`. Just before `ASSIGN_OP` in `bump`, `$x` and `$alias` referred to the same reference containing `int(40)`. Just before `RETURN` they still shared that reference, now containing `int(42)`. The call observer saw `int(42)` returned by `bump` and the two-element integer array `[42, 42]` returned by the file. A separate fixture produced an observed `E_USER_WARNING`, an escaping `RuntimeException` and exit status `255` in both profiles.
