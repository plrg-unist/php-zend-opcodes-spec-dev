## 1. Runtime constant names and values

**Implemented.** Predefined names and their typed values come from execution input by default. Of the 552 names at the pinned CLI, the checked-in reference file supplies 549. Sixteen already received installation values, and this revision moved the other 533 ordinary values out of the rules. A program declaration enters request state when executed. A literal folded during compilation carries its value in the unit. [Input contract and CLI](../design-docs/execution-io.md#runtime-constants) · [Reference data](../runtime-inputs.json) · [Runtime lookup and declaration](../spec/02-vm/20-constants.watsup)

The three case-insensitive global names `TRUE`, `FALSE` and `NULL` belong to the core. PHP uses the first two to spell its two Boolean values and the third to spell the sole value of the null type. Zend recognizes these three before ordinary constant lookup during compilation, and its runtime name resolution also recognizes mixed-case spellings. On the pinned CLI, `defined('NuLl')` returned `true` and `constant('NuLl')` returned `null`. ### Comparison with the Python bytecode spec

At `python-spectec` revision `d595687`, CPython initializes the process and compiles the program before the spec takes over frame evaluation. Its bridge imports the live `sys` module, translates its dictionary and the interpreter's builtins dictionary, and obtains each frame's own builtins mapping. The opcode rules perform ordinary lookup against those objects. Consequently, `sys.maxsize` comes from the host build, `sys.flags.optimize` from the launch, and names such as the Windows-only `sys.winver` can be absent. The corpus exercises both importing `sys.maxsize` and supplying a custom builtins mapping. [Startup bridge](../../python-spectec/python/target/engine/bootstrap.ml#L338) · [Frame inputs](../../python-spectec/python/target/types/frame_type.ml#L108) · [Attribute lookup](../../python-spectec/python-spec/6-eval/6.4.10-bytecode-attribute.spectec#L14) · [Import fixture](../../python-spectec/python/testdata/main/import_star.py#L6) · [Custom mapping fixture](../../python-spectec/python/testdata/main/builtins_mapping.py#L14) · [CPython system parameters](https://docs.python.org/3.14/library/sys.html#sys.maxsize)

The Python spec gives distinguished identities to `None`, `True`, `False` and `NotImplemented`. Its `LOAD_CONST` rule reads the code object's constant pool. CPython folds a bare `__debug__` using the compilation's optimization level. A probe compiled once at optimization level 0 printed `__debug__`, `builtins.__debug__` and `hasattr(builtins, "help")`. On stock CPython 3.12.3 it printed `True True True` normally, `True False True` with `-O`, and `True True False` with `-S`. The Python 3.14 project behavior was checked against its source and fixtures. [Singleton identities](../../python-spectec/python-spec/2-memory/2.1-memory.spectec#L75) · [Constant-load rule](../../python-spectec/python-spec/6-eval/6.4.13-bytecode-constant.spectec#L46) · [CPython compiler](https://github.com/python/cpython/blob/3.14/Python/ast_preprocess.c#L589) · [Builtins added by site](https://docs.python.org/3.14/builtins/constants.html#constants-added-by-the-site-module)

The distinction matters even within one project. A program reading `sys.maxsize` gets the host's value, yet the Python spec's sequence-repetition rules fix an internal limit of `2^63 - 1` and assume eight-byte pointers. For PHP, deciding where a public constant gets its value and justifying any target assumption in an operation are separate questions. [Sequence size limits](../../python-spectec/python-spec/5-builtin/5.06-builtin-list.spectec#L180)

## 2. Floating-point power

**Resolved.** Keep Rust’s `f64::powf` for the target-dependent rounding of floating-point `POW`. The spec defines PHP’s operand conversions, result type, integer overflow promotion and diagnostics. [Foreign-helper policy](../design-docs/foreign-calls.md#operations-delegated-to-c) · [Power rules](../spec/01-values/03-arithmetic.watsup)

With only the script path on the command line, `$argc` is 1. The probe used `$x = 2.4 * $argc; echo (int) ($x ** 11.1 === 16609.04963655714);` to compute the power at runtime. Both Zend and the spec printed `1` with default glibc CPU dispatch and `0` with `GLIBC_TUNABLES=glibc.cpu.hwcaps=-FMA,-FMA4,-AVX2,-AVX,-AVX512F`. Each compiler profile reproduced the change on its own listing, with empty stderr and exit status 0.

On the reference x86-64 Linux build, the Rust evaluator’s `f64::powf` compiles to a call to double-precision C `pow`. The dynamic linker resolved `pow@GLIBC_2.29` in the same `libm.so.6` for Zend and the evaluator. Both returned exactly the binary64 value represented by `16609.049636557142` with default CPU dispatch and the adjacent value `16609.049636557145` with the alternate dispatch. Rust leaves the precision of `powf` unspecified. [Zend’s call to pow](../../php-src/Zend/zend_operators.c#L1415) · [Rust primitive](../src/binary64.rs#L68) · [Rust precision contract](https://doc.rust-lang.org/std/primitive.f64.html#method.powf)

For integer-to-float conversion, Zend uses a C cast from `zend_long` to `double`. The floating-point branches of addition, subtraction, multiplication and division use the corresponding C operators. Zend checks for a zero divisor before executing the division. [Integer cast](../../php-src/Zend/zend_operators.c#L633) · [Float addition](../../php-src/Zend/zend_operators.c#L1218) · [Float division](../../php-src/Zend/zend_operators.c#L1538)

Zend uses other C operations in the implemented opcodes. For a finite float outside the signed 64-bit range, its cast uses `fmod` with divisor 2⁶⁴. In our evaluator, Rust’s `$f64_trunc` returns an arbitrary-precision integer. The P4-SpecTec rule wraps it to signed 64 bits and produces PHP’s range warning. Casting the exactly representable float 2⁶⁴ + 4096 produced the warning and the integer `4096` in both executors under both glibc settings and compiler profiles. PHP’s manual leaves the out-of-range result undefined across targets. [Zend cast](../../php-src/Zend/zend_operators.c#L3940) · [Spec cast](../spec/01-values/02-numeric-conversions.watsup#L209) · [Rust helpers](../design-docs/foreign-calls.md) · [Cast fixture](../tests/project/numeric_casts.php) · [PHP integer conversions](https://www.php.net/manual/en/language.types.integer.php)

PHP ships its decimal conversion routines in `Zend/zend_strtod.c`. The `zend_strtod` parser rounds a decimal to binary64. In the opposite direction, `zend_gcvt` requests digits from `zend_dtoa` and chooses fixed or scientific notation. For the same value of `1 / 3`, `echo` prints `0.33333333333333` at the reference precision of 14, while an implicit float-to-int diagnostic requests the shortest round-tripping digits and prints `0.3333333333333333`. [Decimal parser](../../php-src/Zend/zend_strtod.c#L2517) · [Formatter](../../php-src/Zend/zend_strtod.c#L4534) · [Ordinary output precision](../../php-src/Zend/zend_operators.c#L3670) · [Diagnostic precision](../../php-src/Zend/zend_operators.c#L930)

For `<=>` on two nonnumeric strings, Zend compares bytes up to the shorter length with `memcmp`. The first differing byte determines the order, and length breaks a prefix tie. The spec expresses that order directly. For `-3 >> 1`, Zend uses signed C right shift and the spec explicitly extends the sign, giving `-2`. [Zend byte comparison](../../php-src/Zend/zend_operators.c#L3332) · [Comparison rule](../spec/01-values/05-comparison.watsup#L17) · [Zend right shift](../../php-src/Zend/zend_operators.c#L2078) · [Shift rule](../spec/01-values/04-bitwise.watsup#L47)

## 3. Native byte offsets in switch and match tables

The `.zop` listing records jump-table entries as instruction numbers. In the fixture, `MATCH` at instruction 2 uses a table whose entry for key `0` is `3`. The match jumps to instruction 3. That instruction then reads key `0` from the same table as an ordinary array. Zend stores the byte distance from instruction 2 to instruction 3 in that entry, so the read returns `(3 - 2) * sizeof(zend_op)`. The size here is the size of a whole instruction record. [Fixture](../tests/project/array_dispatch_offsets.zop#L17) · [Listing exporter](../ext/text.c#L316) · [Native listing loader](../ext/instructions.c#L599) · [Zend's table conversion](../../php-src/Zend/zend_opcode.c#L1239)

The three entries target instructions 3, 1 and 2. Reading them as array values on the reference build prints `32,-32,0\n`. A C header probe with `ZEND_VERIFY_TYPE_INFERENCE` measured a 56-byte instruction record and offsets `56,-56,0` for the same targets. With headers produced by Zend's `--with-vm-kind=SWITCH` generator option, a C probe measured 28 bytes normally and 52 with type-inference verification. The switch dispatcher stores its handler as a four-byte integer. Pointers and `zend_long` measured eight bytes in all four configurations. [Zend instruction structure](../../php-src/Zend/zend_compile.h#L137) · [Offset macro](../../php-src/Zend/zend_compile.h#L765) · [VM generator options](../../php-src/Zend/README.md#L128) · [Handler field types](../../php-src/Zend/zend_vm_opcodes.h#L66)

**Implemented.** The spec receives the target build's `sizeof(zend_op)` in bytes as an execution input. The only current semantic calculation that uses it is the ordinary-array read of a `MATCH`, `SWITCH_LONG` or `SWITCH_STRING` table. Fallthrough advances the program counter by one instruction, and branches use body-local instruction numbers directly. [Ordinary array read and table kinds](../spec/02-vm/02-cases.watsup#L3) · [Table branch](../spec/02-vm/02-cases.watsup#L46) · [Instruction fetch and fallthrough](../spec/02-vm/00-core.watsup#L500)

The runtime input parser bounds the size at the largest signed 32-bit forward displacement. Before execution, the Rust validator checks each table entry using the target size and the two instruction indices from the listing. The native loader checks the same signed displacement range using its compiled size. An ordinary array read can therefore return the exact product. The runner passes the size to `$execute`, which keeps it in the frame for `$literal_value` and `$ordinary_array`. [Input contract](../design-docs/execution-io.md#runtime-inputs) · [Rust validation](../src/validate.rs#L944) · [Native validation](../ext/instructions.c#L385) · [Offset calculation](../spec/02-vm/02-cases.watsup#L12)

The repository's reference inputs supply 32 bytes. Both compiler profiles compare the default jump-table cases with Zend. The case with `"opline_size_bytes": 56` sets `"compare_zend": false` and checks the spec against stdout `56,-56,0\n`, empty stderr and exit status 0. With a size of 1073741824, a target two instructions back reads as −2147483648. A target two instructions forward exceeds the signed range at that same size. [Backward and 56-byte cases](../tests/semantics.json#L122) · [Forward overflow](../tests/semantics.json#L110) · [Comparison contract](differential-testing.md#spec-executable-and-differential-suite)

The planned call, exception and generator rules can represent return, handler and resume positions as instruction indices. Exception regions and live ranges already use indices in the listing. Zend itself saves an instruction number for `FAST_CALL` and derives a suspended generator's instruction number when locating its `finally` block. The size would matter to a future rule if it exposed a byte distance to the program. [Listing metadata](../spec/00-syntax.watsup#L127) · [Zend finally return position](../../php-src/Zend/zend_vm_def.h#L8750) · [Generator cleanup](../../php-src/Zend/zend_generators.c#L286)

## 4. Tool nesting limits and well-formedness

**Implemented.** The C exporter, C loader and Rust validator accept structurally valid listings beyond the former nesting cutoffs. The Rust validator checks each expression node and uses a worklist to visit closure bodies, including in uncalled functions. The C tools run on trusted inputs in fresh CLI processes during testing. An unusually deep traversal can exhaust the native stack and terminate that invocation. A diagnostic for that condition can be added if a concrete need arises. [C expression codec](../ext/constant_ast.c) · [C literal codec](../ext/text.c#L514) · [C body codec](../ext/body.c#L295) · [Rust expression validation](../src/validate/expressions.rs) · [Body worklist](../src/validate.rs#L52)

The C tools previously capped constant expressions, literal values and nested child function bodies at depth 256. The loader also capped closure defaults at 64. The Rust validator adopted the loader's expression and closure cutoffs in `9c8be84`. Zend executed a file containing 65 nested closure defaults in an unused function, and the exporter wrote the listing. The loader rejected that same listing, and the Rust validator reported `malformed`. Zend also executed an unused default with 257 nested additions which the exporter refused to write. Both compiler profiles reproduced these results.

The regression fixture puts all four cases in one dormant function. It nests 65 closure defaults, 257 additions, 257 literal arrays and 257 child function bodies. Both compiler profiles export and reload the unit with identical listings. Zend and the spec print `ok\n` with empty stderr and exit status 0. A Rust unit test also checks that an invalid flag at the leaf of a 257-level expression is still rejected for that flag. ## 5. Array layout selection and its observable effects

**Resolved.** Keep the existing packed and mixed array rules in the opcode semantics, including layout selection, growth, compaction, and the resulting append keys and cursor positions. The sizing thresholds are fixed rules of the pinned engine. PHP arrays preserve keys, values and insertion order. Packed storage lets Zend access an integer key by position and avoid a hash lookup. PHP 8.2 made that storage more compact by keeping just the values. [PHP array model](../../php-chunked-xhtml/language.types.array.html#language.types.array) · [Zend implementer’s explanation](https://www.npopov.com/2014/12/22/PHPs-new-hashtable-implementation.html) · [Packed storage change](https://github.com/php/php-src/commit/90b7bde61507cee1c6b37f153909d72f5b203b8c)

Two PHP literals produce the same entries at keys 0 through 3. Repeating `0 => 0` in the first literal gives its packed array 16 slots. The second starts with 8. Writing key 12 keeps the first array packed and converts the second to a mixed table. After unsetting key 12, an immediate append would use key 13 in both. The fixture first inserts key 4. Zend’s packed insertion resets the next key to 5, while the mixed insertion preserves 13. Zend and the spec therefore print `9:-\n-:9\n` with empty stderr and exit status 0 under both compiler profiles. [PHP fixture](../tests/project/array_literal_packed_capacity.phpt) · [Packed insertion](../../php-src/Zend/zend_hash.c#L1327) · [Mixed insertion](../../php-src/Zend/zend_hash.c#L1386)

When a nonnegative integer key exceeds the last allocated slot of a packed array, Zend grows the packed table if the key fits in twice the capacity and more than half the current slots are live. With eight slots, writing key 12 converts to mixed with four live entries and grows to 16 packed slots with five. A different reason for conversion is reinserting a deleted key before a later live key. Zend converts so that iteration visits the reinserted key last. For a compiled array constructor, `INIT_ARRAY` can also carry an initial size and a flag that selects mixed storage from the outset. [Zend growth decision](../../php-src/Zend/zend_hash.c#L1336) · [Zend reinsertion](../../php-src/Zend/zend_hash.c#L1308) · [Spec layout transition](../spec/01-values/10-array-updates.watsup#L28) · [Compiler flag](../../php-src/Zend/zend_compile.c#L11762) · [VM initialization](../../php-src/Zend/zend_vm_def.h#L6544)

The spec represents ordinary runtime arrays with one value containing ordered entries and optional state for the next key, storage layout and cursor. Zend introduced the packed next-key update in a performance optimization. Using one next-key calculation for both layouts, as considered earlier, would produce key 13 for both literals and lose the distinction the user wants to retain. Native replay uses the listing’s layout metadata to reconstruct Zend arrays. [Array value](../spec/01-values/01-core.watsup#L13) · [Zend optimization](https://github.com/php/php-src/commit/f4b7239caeb56d41d4458890b5e7f1f171c7cf6b) · [Layout-dependent update](../spec/01-values/10-array-updates.watsup#L79) · [Native literal layout](opcode-syntax.md#printing-and-parsing-conventions)

### Layout rules in the opcode semantics

Execution starts with one finalized compilation unit, including its operands and literal tables. Compiler and OPcache choices belong to fixture preparation. In a variant of the capacity fixture, we replayed each of two compiled listings unchanged under both native loader profiles. The ordinary listing appended at key 5 in both runs. The optimized listing appended at key 13 in both runs. Each write uses the array state at that instruction. [Execution scope](semantics-scope.md#agreed-boundary) · [Capacity fixture](../tests/project/array_literal_packed_capacity.phpt)

- Honor the layout of a finalized literal. An `INIT_ARRAY` with a first element honors its mixed flag and size hint. An operandless `INIT_ARRAY` starts with its storage undecided. From that state, an initial key of zero and successive integer keys use packed storage, while a sufficiently distant first key may select mixed storage. [Zend initialization](../../php-src/Zend/zend_hash.c#L294) · [Constructor handler](../../php-src/Zend/zend_vm_def.h#L6535) · [Literal metadata](opcode-syntax.md#printing-and-parsing-conventions)
- Keep the constraints imposed by packed storage. Its live keys are nonnegative integers in increasing order, possibly with gaps. An ordinary in-place overwrite or deletion preserves the layout. A new string key after PHP key conversion, a negative index, or filling a gap before a surviving higher key requires mixed storage. Reinserting a removed tail key can stay packed. A forward insertion that fits the existing packed reservation stays packed. A mixed array stays mixed through ordinary in-place writes and unsets, even when its keys again form a list. Copying or rebuilding an array can select fresh storage. [Integer insertion](../../php-src/Zend/zend_hash.c#L1285) · [String insertion](../../php-src/Zend/zend_hash.c#L1074) · [Deletion](../../php-src/Zend/zend_hash.c#L1680) · [Copy](../../php-src/Zend/zend_hash.c#L2674)
- The opcode semantics specifies the minimum reservation of 8 slots, power-of-two sizing, the packed growth test and the full mixed table’s compaction cutoff. It also specifies how rebuilding storage relocates cursors. [Growth and compaction](../spec/01-values/10-array-updates.watsup#L28) · [Cursor relocation](../spec/01-values/15-table-positions.watsup#L31) · [Documented compaction behavior](../../php-chunked-xhtml/migration86.incompatible.html#migration86.incompatible.core.foreach-by-reference)

### Observable effects beyond the append key

**Deleting a key and inserting a string key.** Start with keys `0, 4, 5` in that order. To make a mixed copy in PHP, insert a temporary string key and delete it. Set the internal cursor of each array to key `5` with `end($a)`, then run `unset($a[5])` and `$a['x'] = 'X'`. Both arrays now have keys `0, 4, 'x'` and next append key `6`. Pinned Zend’s `key($a)` returns `null` for the initially packed array and `'x'` for the initially mixed array. Deletion leaves both cursors past the end. Converting the packed array to mixed compacts its two remaining elements into slots 0 and 1 but leaves its exhausted cursor at slot 5. The already mixed array’s cursor is at slot 2, where the new key lands. [Zend conversion](../../php-src/Zend/zend_hash.c#L458) · [Cursor adjustment during compaction](../../php-src/Zend/zend_hash.c#L1616) · [Spec insertion and cursor rules](../spec/01-values/10-array-updates.watsup#L88)

The spec can observe this through an already running by-reference `foreach`. A temporary opcode listing put the initial cursor on the third entry with `cursor=2` and performed the same deletion and insertion. Inside `foreach ($iter as &$value)`, it assigned the result to `$iter` and released the other owner. The loop visited no further entries for the initially packed array and visited `'x'` for the initially mixed array. Both native loader profiles and the spec produced these results. A fresh loop over either final array visits `0, 4, 'x'` in insertion order. [Zend iterator rebinding](../../php-src/Zend/zend_hash.c#L780) · [Spec iterator rebinding](../spec/02-vm/15-foreach.watsup#L100) · [Existing rebind fixture](../tests/project/cursor_layout_rebind.zop)

**Unpacking an empty array.** A second opcode listing started with the same packed destination `['A', 'B']` and its cursor on `'B'`. Only the empty source’s layout varied. With a packed source, `ADD_ARRAY_UNPACK` resets the destination cursor, and rebinding the loop visits `A` then `B`. With a mixed source it visits only `B`. Both native loader profiles and the spec reproduced this. The destination gains no elements and its next append key stays 2. [Zend unpack](../../php-src/Zend/zend_vm_def.h#L6411) · [Packed fill resets the cursor](../../php-src/Zend/zend_hash.h#L1647) · [Spec unpack](../spec/01-values/10-array-updates.watsup#L145)

**Builtins outside the current executable spec.** With `$a = [NAN]`, pinned Zend evaluates `$a === array_values($a)` to `true` for the packed array and `false` after inserting and deleting a temporary string key. The packed case reuses the same array. The mixed case allocates a new array, so strict comparison reaches the two NaNs. The roadmap includes `array_values` in milestone 4. With keys `0, 4, 5` and a fresh `mt_srand(1)` for each call, `array_rand($a)` picks key `5` for packed storage and `4` for dense mixed storage. It samples physical slots in this case. Both compiler profiles reproduced both examples, and the current spec returned `UNSUPPORTED` for both programs. [Zend array_values](../../php-src/ext/standard/array.c#L4555) · [Strict comparison](../../php-src/Zend/zend_operators.c#L2563) · [Zend random key selection](../../php-src/ext/standard/array.c#L6531) · [Milestone 4](semantics-roadmap.md#L28)

### What the PHP manual says about layout

The downloaded manual describes PHP arrays as ordered maps. We found no general rule naming *mixed* as the alternative Zend layout or specifying when insertion, density or capacity selects a layout. The `key()` page describes the current element and the past-the-end result. The PHP 8.6 migration guide does document two effects of compaction and copying. By-reference `foreach` can now visit elements it previously skipped after compaction. During copy-on-write, an internal pointer on a deleted element moves to the next surviving element. These statements concern specific cursor behavior. They leave the timing of compaction open. [PHP array model](../../php-chunked-xhtml/language.types.array.html#language.types.array) · [Key lookup](../../php-chunked-xhtml/function.key.html#refsect1-function.key-returnvalues) · [PHP 8.6 migration guide](../../php-chunked-xhtml/migration86.incompatible.html#migration86.incompatible.core.foreach-by-reference)

Since PHP 8.4, `debug_zval_dump()` reports whether an array is packed. The manual describes the function as a way to inspect Zend implementation details. The pinned engine prints `packed` when the storage flag is set and omits the marker otherwise. With `$a = [1, 2]` and `$b = $a`, inserting then deleting a temporary string key on `$b` leaves `$a === $b` true. Both pass `array_is_list()`, but only `$a` prints the marker. An array with keys 0 and 2 can also print the marker despite the gap. [Debug function](../../php-chunked-xhtml/function.debug-zval-dump.html#refsect1-function.debug-zval-dump-description) · [PHP 8.4 changelog](../../php-chunked-xhtml/function.debug-zval-dump.html#refsect1-function.debug-zval-dump-changelog) · [List predicate](../../php-chunked-xhtml/function.array-is-list.html#refsect1-function.array-is-list-description) · [Zend diagnostic](../../php-src/ext/standard/var.c#L374)

The manual calls the output of `UnitEnum::cases()` a packed array in declaration order. On the pinned CLI a nonempty enum produces the debug marker, while an empty enum yields an empty list with no marker. ### Comparison with the PHP 5 K semantics

KPHP represents an array as an ordered list of entries and an iteration cursor. Each literal starts empty. A write to an existing key updates its value in place, a new key goes at the end, and `unset` removes the entry. These rules preserve insertion order without tracking reserved slots or a packed/mixed layout. [K array representation](../../kphp-sources/memory.k#L31) · [Literal construction](../../kphp-sources/arrays.k#L39) · [Existing key](../../kphp-sources/memory.k#L783) · [New key](../../kphp-sources/memory.k#L399) · [Deletion](../../kphp-sources/core.k#L623)

For `$a[]`, KPHP scans the entries still present for the greatest integer key, starting at −1, then adds one. Tracing the fixture's array operations in PHP 5 syntax therefore gives key **5 for both**. Deleting key 12 removes it from the calculation, and the subsequent write makes 4 the greatest live key. PHP 5.3.26, the version cited in the KPHP paper, already kept a separate next-key counter. Its insertion and deletion code imply **13 for both** in this example. Pinned Zend 8.6 and our current spec give **5 and 13** under both compiler profiles. The KPHP and historical Zend results are derived from source. ### Storage-dependent behavior in CPython and its bytecode spec

We ran these comparisons on stock CPython 3.14.0 and on the same interpreter with the unmodified `python-spectec` hook at `d595687`. The project's attribute-deletion and tuple-repetition tests produced their expected distinct native and spec outputs, confirming the hook was active. [Differential test expectations](../../python-spectec/python/target/scripts/pep523_canary_check.py#L138)

**Dictionary literals.** `{k: 1}` and a literal repeating the same `k: 1` six times contain the identical key object and value. Define the key's `__hash__` to return 224 and its `__eq__` to print `eq` and return `self is other`. A membership test with a fresh key returns `False` for both dictionaries. On CPython it prints `eq` twice for the small literal and once for the larger one. CPython sizes each table from the number of written pairs. At eight slots the lookup revisits the stored key, whereas at sixteen slots its second probe reaches an empty slot. The spec's `BUILD_MAP` creates an empty native dict and inserts one pair at a time. Six assignments to the same existing key keep that dict small. We observed two comparisons for both literals under the hook even though the later lookup runs in CPython. This particular callback count has no explicit decision in the project's difference notes. ## 6. Array sharing and comparison

With `$x = [NAN]; $y = $x;`, `$x === $y` is true because the variables initially share an array. `unset($y['missing'])` separates the shared array before checking whether the key exists. Both arrays still contain the single entry `0 => NAN`. The next strict comparison reaches the entries, where `NAN === NAN` is false. Printing the two results as integers produced `10` in both Zend and the spec for the ordinary and optimized listings. ## 7. Decimal conversions

- **Exponent cutoff.** A string consisting of `1`, 20,000 zeroes and `e-20000` represents exactly one. Casting it to float and printing it produced `10` in Zend and the spec under both profiles. Zend caps the explicit exponent at ±19,999 before accounting for the mantissa, a precaution for 16-bit integers. Decimal conversion without that cutoff would print `1`. [Zend cutoff](../../php-src/Zend/zend_strtod.c#L2695) · [Rust parser](../src/binary64.rs#L114)
- **Incomplete signed exponent.** `"9300000000000000000e+" + 0` emits `A non-numeric value encountered` and yields the integer `-9146744073709551616`. Zend advances the scan position past the `e` before checking the 19-digit prefix for overflow. The prefix exceeds the signed 64-bit integer range. Applying the manual’s leading-numeric-string rule would preserve the warning and yield the positive float `9.3e18`. [Spec range check](../spec/01-values/02-numeric-conversions.watsup#L88) · [Zend scanner](../../php-src/Zend/zend_operators.c#L3743) · [Fixture](../tests/project/numeric_decimal_limits.php) · [PHP numeric strings](../../php-chunked-xhtml/language.types.numeric-strings.html#language.types.numeric-strings)

**Resolved.** Keep the ±19,999 cutoff for explicit decimal exponents and Zend’s integer range check for an incomplete signed exponent as part of the opcode semantics. Both rules affect observable results and have been stable throughout PHP 8. On the same finalized listing, the spec and both native loader profiles agreed on both values and the `E_WARNING` from the addition, with empty stderr and exit status 0.

**Implemented.** Each array literal carries Zend’s immutability flag in the finalized unit.
