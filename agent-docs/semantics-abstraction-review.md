# Execution abstraction review

This review covers the implementation through milestone 3D at `36665e6` and the pinned PHP 8.6.0 CLI. Two earlier decisions provide the baseline. At that point the spec abstracted automatic cycle collection timing and received 16 installation constant values as inputs. [Cycle collection decision](../design-docs/automatic-cycle-collection.md) · [Execution inputs](../design-docs/execution-io.md) · [PHP build and compiler profiles](fixture-compilation.md)

Each **Open** entry contains a review recommendation awaiting the user's decision. Update the entry in place as it is discussed and link the resulting design record where applicable. [How observable differences are decided](semantics-scope.md#choosing-what-to-model)

## 1. Runtime constant names and values

**Implemented.** Predefined names and their typed values come from execution input by default. Of the 552 names at the pinned CLI, the checked-in reference file supplies 549. Sixteen already received installation values, and this revision moved the other 533 ordinary values out of the rules. A program declaration enters request state when executed. A literal folded during compilation carries its value in the unit. [Input contract and CLI](../design-docs/execution-io.md#runtime-constants) · [Reference data](../runtime-inputs.json) · [Runtime lookup and declaration](../spec/02-vm/21-constants.watsup)

The three case-insensitive global names `TRUE`, `FALSE` and `NULL` belong to the core. PHP uses the first two to spell its two Boolean values and the third to spell the sole value of the null type. Zend recognizes these three before ordinary constant lookup during compilation, and its runtime name resolution also recognizes mixed-case spellings. On the pinned CLI, `defined('NuLl')` returned `true` and `constant('NuLl')` returned `null`. [PHP Boolean literals](https://www.php.net/manual/en/language.types.boolean.php) · [PHP null literal](https://www.php.net/manual/en/language.types.null.php) · [Compiler substitution](../../php-src/Zend/zend_compile.c#L1703) · [Runtime lookup](../../php-src/Zend/zend_constants.c#L222)

The differential suite checks `GLOB_MARK` against explicit expected values of `8` and `2` on the same finalized listing. It also exercises a missing name, a defined `null`, a long namespaced name, tagged values, deprecation messages and a folded literal. [Per-run test inputs](differential-testing.md) · [Regression fixture](../tests/project/runtime_constant_inputs.php) · [Replacement table](../tests/project/runtime_inputs_subset.json)

The following probes used runtime lookups so that each comparison executed the same finalized listing. All runs had empty stderr and exit status 0.

### Comparison with the Python bytecode spec

At `python-spectec` revision `d595687`, CPython initializes the process and compiles the program before the spec takes over frame evaluation. Its bridge imports the live `sys` module, translates its dictionary and the interpreter's builtins dictionary, and obtains each frame's own builtins mapping. The opcode rules perform ordinary lookup against those objects. Consequently, `sys.maxsize` comes from the host build, `sys.flags.optimize` from the launch, and names such as the Windows-only `sys.winver` can be absent. The corpus exercises both importing `sys.maxsize` and supplying a custom builtins mapping. [Startup bridge](../../python-spectec/python/target/engine/bootstrap.ml#L338) · [Frame inputs](../../python-spectec/python/target/types/frame_type.ml#L108) · [Attribute lookup](../../python-spectec/python-spec/6-eval/6.4.10-bytecode-attribute.spectec#L14) · [Import fixture](../../python-spectec/python/testdata/main/import_star.py#L6) · [Custom mapping fixture](../../python-spectec/python/testdata/main/builtins_mapping.py#L14) · [CPython system parameters](https://docs.python.org/3.14/library/sys.html#sys.maxsize)

The Python spec gives distinguished identities to `None`, `True`, `False` and `NotImplemented`. Its `LOAD_CONST` rule reads the code object's constant pool. CPython folds a bare `__debug__` using the compilation's optimization level. A probe compiled once at optimization level 0 printed `__debug__`, `builtins.__debug__` and `hasattr(builtins, "help")`. On stock CPython 3.12.3 it printed `True True True` normally, `True False True` with `-O`, and `True True False` with `-S`. The Python 3.14 project behavior was checked against its source and fixtures. [Singleton identities](../../python-spectec/python-spec/2-memory/2.1-memory.spectec#L75) · [Constant-load rule](../../python-spectec/python-spec/6-eval/6.4.13-bytecode-constant.spectec#L46) · [CPython compiler](https://github.com/python/cpython/blob/3.14/Python/ast_preprocess.c#L589) · [Builtins added by site](https://docs.python.org/3.14/builtins/constants.html#constants-added-by-the-site-module)

The distinction matters even within one project. A program reading `sys.maxsize` gets the host's value, yet the Python spec's sequence-repetition rules fix an internal limit of `2^63 - 1` and assume eight-byte pointers. For PHP, deciding where a public constant gets its value and justifying any target assumption in an operation are separate questions. [Sequence size limits](../../python-spectec/python-spec/5-builtin/5.06-builtin-list.spectec#L180)

## 2. Floating-point power

**Resolved.** Keep Rust’s `f64::powf` for the target-dependent rounding of floating-point `POW`. The spec defines PHP’s operand conversions, result type, integer overflow promotion and diagnostics. [Foreign-helper policy](../design-docs/foreign-calls.md#operations-delegated-to-c) · [Power rules](../spec/01-values/03-arithmetic.watsup)

With only the script path on the command line, `$argc` is 1. The probe used `$x = 2.4 * $argc; echo (int) ($x ** 11.1 === 16609.04963655714);` to compute the power at runtime. Both Zend and the spec printed `1` with default glibc CPU dispatch and `0` with `GLIBC_TUNABLES=glibc.cpu.hwcaps=-FMA,-FMA4,-AVX2,-AVX,-AVX512F`. Each compiler profile reproduced the change on its own listing, with empty stderr and exit status 0.

On the reference x86-64 Linux build, the Rust evaluator’s `f64::powf` compiles to a call to double-precision C `pow`. The dynamic linker resolved `pow@GLIBC_2.29` in the same `libm.so.6` for Zend and the evaluator. Both returned exactly the binary64 value represented by `16609.049636557142` with default CPU dispatch and the adjacent value `16609.049636557145` with the alternate dispatch. Rust leaves the precision of `powf` unspecified. [Zend’s call to pow](../../php-src/Zend/zend_operators.c#L1415) · [Rust primitive](../src/binary64.rs#L68) · [Rust precision contract](https://doc.rust-lang.org/std/primitive.f64.html#method.powf)

For integer-to-float conversion, Zend uses a C cast from `zend_long` to `double`. The floating-point branches of addition, subtraction, multiplication and division use the corresponding C operators. Zend checks for a zero divisor before executing the division. [Integer cast](../../php-src/Zend/zend_operators.c#L633) · [Float addition](../../php-src/Zend/zend_operators.c#L1218) · [Float division](../../php-src/Zend/zend_operators.c#L1538)

Zend uses other C operations in the implemented opcodes. For a finite float outside the signed 64-bit range, its cast uses `fmod` with divisor 2⁶⁴. In our evaluator, Rust’s `$f64_trunc` returns an arbitrary-precision integer. The P4-SpecTec rule wraps it to signed 64 bits and produces PHP’s range warning. Casting the exactly representable float 2⁶⁴ + 4096 produced the warning and the integer `4096` in both executors under both glibc settings and compiler profiles. PHP’s manual leaves the out-of-range result undefined across targets. [Zend cast](../../php-src/Zend/zend_operators.c#L3940) · [Spec cast](../spec/01-values/02-numeric-conversions.watsup#L209) · [Rust helpers](../design-docs/foreign-calls.md) · [Cast fixture](../tests/project/numeric_casts.php) · [PHP integer conversions](https://www.php.net/manual/en/language.types.integer.php)

PHP ships its decimal conversion routines in `Zend/zend_strtod.c`. The `zend_strtod` parser rounds a decimal to binary64. In the opposite direction, `zend_gcvt` requests digits from `zend_dtoa` and chooses fixed or scientific notation. For the same value of `1 / 3`, `echo` prints `0.33333333333333` at the reference precision of 14, while an implicit float-to-int diagnostic requests the shortest round-tripping digits and prints `0.3333333333333333`. [Decimal parser](../../php-src/Zend/zend_strtod.c#L2517) · [Formatter](../../php-src/Zend/zend_strtod.c#L4534) · [Ordinary output precision](../../php-src/Zend/zend_operators.c#L3670) · [Diagnostic precision](../../php-src/Zend/zend_operators.c#L930)

For `<=>` on two nonnumeric strings, Zend compares bytes up to the shorter length with `memcmp`. The first differing byte determines the order, and length breaks a prefix tie. The spec expresses that order directly. For `-3 >> 1`, Zend uses signed C right shift and the spec explicitly extends the sign, giving `-2`. [Zend byte comparison](../../php-src/Zend/zend_operators.c#L3332) · [Comparison rule](../spec/01-values/05-comparison.watsup#L17) · [Zend right shift](../../php-src/Zend/zend_operators.c#L2078) · [Shift rule](../spec/01-values/04-bitwise.watsup#L47)

### Comparison with Python floating-point power

At `python-spectec` revision `d595687`, the bytecode rules define which operand’s `__pow__` or `__rpow__` method runs. For two ordinary floats, the native bridge calls CPython’s actual `float.__pow__`. CPython handles Python-specific cases such as raising `ZeroDivisionError` for `0.0 ** -1.0` and calls the platform’s `pow` for ordinary positive finite inputs. Elsewhere the project spells out numeric behavior in its own rules, including why `-7 // 2` gives `-4`. [Operator dispatch](../../python-spectec/python-spec/4-protocol/4.04-protocol-operator.spectec#L216) · [Native fallback](../../python-spectec/python-spec/5-builtin/5.09-builtin-callable.spectec#L129) · [CPython 3.14 float power](https://github.com/python/cpython/blob/v3.14.0/Objects/floatobject.c#L719-L779) · [Integer division rule](../../python-spectec/python-spec/5-builtin/5.05-builtin-int.spectec#L15)

An isolated run of the project’s foreign-call stub against the available CPython 3.12.3 returned binary64 encodings `0x40d038432d3ecf67` and `0x40d038432d3ecf68` for `(2.4).__pow__(11.1)` under the two glibc settings. The full CPython 3.14 hook was unavailable locally. [Foreign-call stub](../../python-spectec/python/target/ffi/ffi_call_stubs.c#L80) · [Target requirements](../../python-spectec/python/target/pyconfig/pyflags.py#L21)

## 3. Native byte offsets in switch and match tables

The `.zop` listing records jump-table entries as instruction numbers. In the fixture, `MATCH` at instruction 2 uses a table whose entry for key `0` is `3`. The match jumps to instruction 3. That instruction then reads key `0` from the same table as an ordinary array. Zend stores the byte distance from instruction 2 to instruction 3 in that entry, so the read returns `(3 - 2) * sizeof(zend_op)`. The size here is the size of a whole instruction record. [Fixture](../tests/project/array_dispatch_offsets.zop#L17) · [Listing exporter](../ext/text.c#L316) · [Native listing loader](../ext/instructions.c#L599) · [Zend's table conversion](../../php-src/Zend/zend_opcode.c#L1239)

The three entries target instructions 3, 1 and 2. Reading them as array values on the reference build prints `32,-32,0\n`. A C header probe with `ZEND_VERIFY_TYPE_INFERENCE` measured a 56-byte instruction record and offsets `56,-56,0` for the same targets. With headers produced by Zend's `--with-vm-kind=SWITCH` generator option, a C probe measured 28 bytes normally and 52 with type-inference verification. The switch dispatcher stores its handler as a four-byte integer. Pointers and `zend_long` measured eight bytes in all four configurations. [Zend instruction structure](../../php-src/Zend/zend_compile.h#L137) · [Offset macro](../../php-src/Zend/zend_compile.h#L765) · [VM generator options](../../php-src/Zend/README.md#L128) · [Handler field types](../../php-src/Zend/zend_vm_opcodes.h#L66)

**Implemented.** The spec receives the target build's `sizeof(zend_op)` in bytes as an execution input. The only current semantic calculation that uses it is the ordinary-array read of a `MATCH`, `SWITCH_LONG` or `SWITCH_STRING` table. Fallthrough advances the program counter by one instruction, and branches use body-local instruction numbers directly. [Ordinary array read and table kinds](../spec/02-vm/02-cases.watsup#L3) · [Table branch](../spec/02-vm/02-cases.watsup#L46) · [Instruction fetch and fallthrough](../spec/02-vm/00-core.watsup#L500)

The runtime input parser bounds the size at the largest signed 32-bit forward displacement. Before execution, the Rust validator checks each table entry using the target size and the two instruction indices from the listing. The native loader checks the same signed displacement range using its compiled size. An ordinary array read can therefore return the exact product. The runner passes the size to `$execute`, which keeps it in the frame for `$literal_value` and `$ordinary_array`. [Input contract](../design-docs/execution-io.md#runtime-inputs) · [Rust validation](../src/validate.rs#L944) · [Native validation](../ext/instructions.c#L385) · [Offset calculation](../spec/02-vm/02-cases.watsup#L12)

The repository's reference inputs supply 32 bytes. Both compiler profiles compare the default jump-table cases with Zend. The case with `"opline_size_bytes": 56` sets `"compare_zend": false` and checks the spec against stdout `56,-56,0\n`, empty stderr and exit status 0. With a size of 1073741824, a target two instructions back reads as −2147483648. A target two instructions forward exceeds the signed range at that same size. [Backward and 56-byte cases](../tests/semantics.json#L122) · [Forward overflow](../tests/semantics.json#L110) · [Comparison contract](differential-testing.md#spec-executable-and-differential-suite)

The planned call, exception and generator rules can represent return, handler and resume positions as instruction indices. Exception regions and live ranges already use indices in the listing. Zend itself saves an instruction number for `FAST_CALL` and derives a suspended generator's instruction number when locating its `finally` block. The size would matter to a future rule if it exposed a byte distance to the program. [Listing metadata](../spec/00-syntax.watsup#L127) · [Zend finally return position](../../php-src/Zend/zend_vm_def.h#L8750) · [Generator cleanup](../../php-src/Zend/zend_generators.c#L286)

## 4. Tool nesting limits and well-formedness

**Implemented.** The C exporter, C loader and Rust validator accept structurally valid listings beyond the former nesting cutoffs. The Rust validator checks each expression node and uses a worklist to visit closure bodies, including in uncalled functions. The C tools run on trusted inputs in fresh CLI processes during testing. An unusually deep traversal can exhaust the native stack and terminate that invocation. A diagnostic for that condition can be added if a concrete need arises. [C expression codec](../ext/constant_ast.c) · [C literal codec](../ext/text.c#L514) · [C body codec](../ext/body.c#L295) · [Rust expression validation](../src/validate/expressions.rs) · [Body worklist](../src/validate.rs#L52)

The C tools previously capped constant expressions, literal values and nested child function bodies at depth 256. The loader also capped closure defaults at 64. The Rust validator adopted the loader's expression and closure cutoffs in `9c8be84`. Zend executed a file containing 65 nested closure defaults in an unused function, and the exporter wrote the listing. The loader rejected that same listing, and the Rust validator reported `malformed`. Zend also executed an unused default with 257 nested additions which the exporter refused to write. Both compiler profiles reproduced these results.

The regression fixture puts all four cases in one dormant function. It nests 65 closure defaults, 257 additions, 257 literal arrays and 257 child function bodies. Both compiler profiles export and reload the unit with identical listings. Zend and the spec print `ok\n` with empty stderr and exit status 0. A Rust unit test also checks that an invalid flag at the leaf of a 257-level expression is still rejected for that flag. [PHP fixture](../tests/project/deeply_nested_unit.phpt) · [Semantic expectation](../tests/semantics.json#L367) · [Expression tests](../src/tests.rs#L915)

## 5. Array capacity and the next append key

Two PHP literals produce the same entries at keys 0 through 3. Repeating a key in the first literal reserves more storage. Both arrays then write and unset key 12, write key 4, and append. In both compiler profiles Zend and the spec append at key **5** for the wider array and **13** for the smaller one. The fixture prints `9:-\n-:9\n`, with empty stderr and status 0. Zend introduced the packed-array update in a performance optimization. Matching it requires the spec to track capacity and when sparse writes change the table representation. [PHP fixture](../tests/project/array_literal_packed_capacity.phpt) · [Spec updates](../spec/01-values/10-array-updates.watsup#L28) · [Zend optimization](https://github.com/php/php-src/commit/f4b7239caeb56d41d4458890b5e7f1f171c7cf6b)

**Open.** The review recommends retaining the highest assigned integer key across these ordinary writes and deletions, as described in the PHP manual. Both appends would use key 13 and the fixture would print `-:9\n-:9\n`. This would be a deliberate difference from pinned Zend. Native replay can retain exact layout metadata. Iteration order, cursor behavior and reference effects need their own witnesses when considering any further simplification. [PHP array append rule](https://www.php.net/manual/en/language.types.array.php#language.types.array.syntax.modifying) · [Physical cursor fixture](../tests/project/cursor_layout_rebind.zop)

## 6. Array sharing and comparison

With `$x = [$argc * NAN]; $y = $x;`, the comparison `$x === $y` is true. After `unset($y['absent'])`, it is false. Unsetting the missing key leaves every entry in place and causes Zend to separate the backing tables. Printing the two comparison results as integers produced `10` in Zend and the spec under both profiles, with empty stderr and status 0. Zend introduced the same-table shortcut as a comparison optimization. [Spec identity check](../spec/01-values/08-array-comparison.watsup#L97) · [Missing-key unset fixture](../tests/project/copy_on_write_noop.php) · [Zend optimization](https://github.com/php/php-src/commit/d57b278ad1f490094b0c3331cf02312b785a8a78)

**Open.** The review favors retaining the pinned result for now. An entry-wise comparison of these acyclic arrays would print `00`, since `NAN` compares unequal to itself. This choice is independent of the append key. A recursive array comparing identical to itself is also covered by an upstream regression. [PHP array comparisons](https://www.php.net/manual/en/language.operators.array.php) · [Recursive comparison regression](../../php-src/Zend/tests/recursive_array_comparison.phpt)

## 7. Decimal conversions

- **Exponent cutoff.** A string consisting of `1`, 20,000 zeroes and `e-20000` represents exactly one. Casting it to float and printing it produced `10` in Zend and the spec under both profiles. Zend caps the explicit exponent at ±19,999 before accounting for the mantissa, a precaution for 16-bit integers. Decimal conversion without that cutoff would print `1`. [Zend cutoff](../../php-src/Zend/zend_strtod.c#L2695) · [Rust parser](../src/binary64.rs#L114)
- **Incomplete signed exponent.** `"9300000000000000000e+" + 0` emits a warning and yields the integer `-9146744073709551616`. Zend advances the scan position past the `e` before checking the 19-digit prefix for overflow. Applying the documented leading-numeric-string rule would preserve the warning and yield a positive float. [Spec range check](../spec/01-values/02-numeric-conversions.watsup#L88) · [Zend scanner](../../php-src/Zend/zend_operators.c#L3743) · [Fixture](../tests/project/numeric_decimal_limits.php) · [PHP numeric strings](https://www.php.net/manual/en/language.types.numeric-strings.php)

**Open.** Both observations were repeatable on the pinned target. Changing either conversion is a separate compatibility decision with an observable result.
